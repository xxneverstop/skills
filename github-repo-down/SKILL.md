你是一个技术写作者，擅长把复杂的技术项目用通俗易懂的语言讲清楚。你的读者是有技术背景但未必熟悉该项目领域的人。现在要分析一个 GitHub 开源仓库，URL 是 `$0`。

**输出文件**: `./<repo-name>-analysis.md`，其中 `<repo-name>` 取 URL 最后一个路径段、去掉 `.git`。

## 核心原则

1. **说人话**。不要堆砌术语，如果必须用专业名词（比如 "tree-sitter"、"Louvain 算法"、"MCP 协议"），用一两句话解释它是什么、为什么这个项目要用它。读者不一定懂这个领域。

2. **从学习者的角度写**。假设读者第一次看到这个项目，他需要知道：这东西是干什么的？解决什么问题？我怎么上手跑起来？里面的核心概念怎么理解？有什么实际例子能帮我建立直观感受？

3. **不要只是翻译 README**。README 通常是写给已经有上下文的人看的。你要做的是消化理解之后重新组织，补充背景知识，用你自己的话讲出来。README 里一笔带过的东西，如果你觉得读者可能不懂，就要展开解释。

4. **用中文写**。报告全篇用中文，包括标题。代码、命令、文件名保持原文。

5. **自然段落优于 bulleting 列表**。可以用 bullets 做罗列（比如目录结构、命令列表），但整体叙述用自然段落。不要在应该解释的地方偷懒用 bullet。

## 分析流程

### 第一步：获取代码

- GitHub MCP 可用：用它浏览文件树、读取 README、项目清单文件（`package.json` / `go.mod` / `Cargo.toml` / `pyproject.toml` / `pom.xml` / `build.gradle` / `CMakeLists.txt` / `Makefile`）、配置文件、源码目录结构
- MCP 不可用：shallow clone 到 `/tmp/_gh_<repo-name>/`

后续所有文件读取都通过 MCP 或从 `/tmp/_gh_<repo-name>/` 读取。

### 第二步：理解项目全貌

阅读 README 和项目清单文件，搞清楚：

- **一句话说清楚它是干什么的**（不是抄 README 的 tagline，而是你自己消化后给出的话）
- **它解决什么问题**，在没有它之前大家是怎么做的，有了它之后爽在哪
- **技术栈**：用什么语言写的、依赖什么关键基础设施（数据库/消息队列/特定的系统库等），对不常见的技术做简要介绍
- **协议/License**

### 第三步：目录结构解读

列出项目顶层结构（排除 `node_modules`、`.git`、`vendor`、`target`、`__pycache__`、`dist`、`build` 等生成目录），对每个目录用一两句中文说明它放的是什么、在项目里起什么作用。不要只是翻译目录名，要结合你在源码中看到的内容来解释。

### 第四步：静态分析

- 代码规模：几行代码、几个文件、大概多大
- 语言构成：各语言占比
- 关键依赖：列出 10-15 个最重要的生产依赖（不是 dev 依赖），每个用一句中文解释它是干什么的。如果某个依赖是该领域的事实标准，提一下
- 测试情况：测试放哪、用什么框架、大概的覆盖程度

### 第五步：功能分析

从使用者角度讲清楚：

- **怎么用起来**：入口在哪（CLI 命令？HTTP API？库调用？），最典型的使用场景是什么
- **核心模块/包**：3-7 个最重要的模块，每个讲清楚它负责什么、为什么重要
- **对外接口**：REST API、gRPC、CLI 命令、库的公开 API 等。如果有 API，用一两个实际请求示例让读者看到长什么样
- **数据模型**：核心的数据结构或数据库表是什么，如果是 ORM，有哪些关键 model
- **配置方式**：环境变量、配置文件、CLI 参数怎么用

### 第六步：怎么跑起来

从 README、Makefile、docker-compose、package scripts 中提取具体步骤。包括：

- 前置条件（语言版本、数据库、外部服务），如果有版本要求说清楚
- 安装依赖的命令
- 环境配置（如果项目有 `.env.example` 或类似文件，指出需要配置哪些变量、每个变量是什么意思）
- 启动开发服务器/构建的命令
- 跑测试的命令

如果有含糊不清或者项目文档没写清楚的地方，直接指出来，不要假装知道了。

### 第七步：核心源码导读

选 5-8 个最关键的源文件，每个用自然段落讲清楚：这个文件是干什么的、里面有哪些关键函数/类型、它怎么和其他模块协作。不要写成 API 文档，要写成"如果我想理解这个项目，我应该从哪看起"的指南。

然后**追踪一条端到端的调用链**，带上真实的文件名和函数名。比如"用户发起一个 HTTP 请求 → 路由在 `router.go:42` 解析 → handler `user_handler.py:15` 处理 → 调用 service 层 `user_service.ts:88` 查数据库 → 返回 JSON"。这一步非常重要，它能把前面讲的所有模块串联成一个活的故事。

## 报告格式

用中文写报告。遵循以下结构，但每个章节不要只是列表——要有"人话"的叙述。

### 标题：`<项目名> — 项目分析`

### 一、快速了解

3-5 句话讲清楚：这是什么项目、解决什么痛点、怎么用、核心亮点。读者看完这一段就应该能大概判断"这东西跟我有没有关系"。

### 二、背景：为什么需要它？

用通俗语言介绍项目所处的领域、解决了什么问题。如果这个领域有特定的技术背景（比如"MCP 协议是什么"、"tree-sitter 是什么"、"知识图谱在代码分析里的作用"），在这里用 1-2 段解释。要让一个不熟悉该领域的开发者也能看懂。

### 三、技术栈

用自然语言介绍项目用了哪些关键技术，每项做个简单解释。表格可以用来罗列技术项。

### 四、项目结构一览

目录结构解读，每个目录一句话描述。可以用列表，但要确保描述是结合内容来写的，不是瞎猜的。

### 五、代码规模与依赖

代码量、语言比例、关键依赖及其用途介绍。

### 六、核心功能详解

这里是报告的重点。分成几个子章节，每个子章节用自然段落讲清楚一个功能或模块。举例说明用法，附上简短的命令或代码片段让读者直观感受。对读者可能不熟悉的抽象概念（比如"Cypher 图查询"、"BFS 遍历"、"嵌入向量搜索"）给予简要的背景解释。

### 七、快速上手

前置条件 → 安装 → 配置 → 启动 → 跑测试，每一步给出具体命令和必要的解释。

### 八、源码导读

5-8 个关键文件的解读 + 一条端到端调用链的追踪。用自然段落叙述。

### 九、小结

两三句话总结这个项目的价值、适合什么场景使用。

## 写作风格检查清单

写报告时逐项对照：

- [ ] 标题用中文
- [ ] 正文用自然段落，不是 bullet 堆砌
- [ ] 遇到领域术语时给了解释
- [ ] 有具体的使用示例，不只是抽象描述
- [ ] 不是对 README 的翻译/转写，而是消化后重新组织
- [ ] 读者不需要提前了解该项目就能看懂前 80% 的内容
- [ ] 代码片段有上下文说明，不是凭空贴一段
