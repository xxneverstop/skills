# 用大白话讲清楚代码项目

## 目标

把一个陌生项目讲到读者能够回答这些问题：

- 这个项目解决什么问题？
- 主要模块分别负责什么？
- 一条核心数据或请求如何从入口走到结果？
- 专业名词、英文缩写和关键代码对象分别是什么意思？
- 哪些地方负责做决定，哪些地方真正执行工作？
- 失败、重试、回滚、版本替代或人工介入如何发生？
- 如果要继续读代码，应该先看哪些文件？

默认只做只读分析和说明。只有用户明确要求修改代码、生成文档或保存结果时，才执行相应写入操作。

## 适用场景

当用户提出下面这类请求时使用本 Skill：

- “帮我理解这个项目的整体架构”；
- “解释一下这个代码库怎么运行”；
- “把这套系统用容易懂的方式讲清楚”；
- “分析一条数据从哪里来、经过什么处理、最后到哪里”；
- “给新人写一份项目导读”；
- “把专业术语都解释一下”。

## 分析方法

先读取项目根目录的 `AGENTS.md`、`CLAUDE.md`、`README.md` 和明显相关的设计文档，遵守其中的项目约定。查看当前工作区状态时只读，不要覆盖已有改动。

代码发现优先使用项目指定的知识图谱、索引或语义搜索工具。如果项目的说明明确要求使用 `codebase-memory-mcp`，优先按以下顺序使用：

1. `search_graph`：查找函数、类、路由、变量和入口；
2. `trace_path`：追踪调用者、被调用者和数据流；
3. `get_code_snippet`：读取已经定位到的函数或类；
4. `query_graph`：查询多跳关系、依赖和聚合信息；
5. `get_architecture`：获取高层架构概览。

如果知识图谱不可用，再使用 `rg`、`rg --files` 和定点读取文件。字符串、配置值、Dockerfile、脚本和非代码文档仍然可以直接用文本搜索。

先找入口和主链路，再补模块细节。通常需要检查：

- 启动入口、HTTP 路由、命令行入口和后台任务；
- 核心业务对象、数据库模型和状态字段；
- 配置文件、队列、消息、缓存、文件存储和外部服务；
- 关键 Worker、Service、Controller、Repository 或 Pipeline；
- 测试、部署文件和高信号文档。

区分三种结论：

- **已确认**：能在代码、配置、测试或文档中直接找到依据；
- **合理推断**：由多个代码事实推导出来，明确写出这是推断；
- **待确认**：仓库中没有足够证据，说明需要运行环境、日志或人工确认。

不要把目录名称直接当成真实架构。要结合调用关系、数据读写和部署配置，说明模块在实际链路中的作用。

## 推荐讲解顺序

根据项目大小增减章节，但优先按照下面的顺序组织内容：

### 1. 先用一句话说明项目

先说明项目服务谁、解决什么问题、输入是什么、输出是什么。给读者一个 30 秒内能建立的整体印象。

### 2. 给出总链路

用一条短流程表示核心路径，例如：

```text
输入
  → 接收或登记
  → 核心处理
  → 校验或人工确认
  → 输出或交付
```

如果存在并行分支、重试或反馈回路，使用小型 Mermaid 图或 ASCII 图表示。图只画代码中确认存在的组件，通常控制在 3 到 10 个节点。

### 3. 拆分系统边界和模块职责

说明每个主要目录、服务或进程负责什么，以及它与其他模块如何连接。重点区分：

- 接收请求和保存事实的模块；
- 编排任务和决定下一步的模块；
- 真正执行耗时工作的 Worker；
- 给人查看、操作或审核的界面；
- 保存结构化状态的数据库和保存大文件的存储。

### 4. 解释核心名词

专业词第一次出现时，使用“英文名词 + 中文含义 + 直白解释 + 在本项目中的作用”的格式。例如：

> `Episode`（一次完整的机器人操作记录）：可以把它理解成一个档案盒，里面包括这次操作产生的原始文件、转换结果、标注和质检记录。

解释缩写、状态、队列、租约、版本、快照、幂等、DAG、代理文件和领域对象。之后可以直接使用已经解释过的名词。

不要为了形式解释所有普通编程词。优先解释读者不熟悉、会影响理解的领域词、系统词和代码中的关键对象。

### 5. 跟踪一条具体数据或请求

选择一个具体对象，例如一条订单、一条 Episode、一次上传或一个任务，从创建、存储、处理、校验到最终结果完整走一遍。每一步回答：

- 谁触发；
- 读取什么；
- 做了什么；
- 写入什么；
- 下一步由谁触发；
- 失败后如何处理。

具体例子优先于抽象描述，但例子必须和代码事实一致。若使用假设例子，要明确标注“举例”。

### 6. 解释状态、队列和异常路径

说明整体对象状态和单个任务状态是否分开，谁负责写状态，谁负责根据明细派生状态。解释任务如何进入队列、如何领取、如何防止重复处理、租约过期后如何恢复，以及哪些失败会重试、哪些失败需要人工处理。

### 7. 说明运行和部署方式

只在与理解链路有关时介绍容器、Pod、Deployment、Job、Kubernetes、自动扩缩容、数据库、对象存储和反向代理。每个术语第一次出现都给出直白解释。

### 8. 给出代码阅读路线

按“先读什么、为了理解什么、接着看什么”的顺序列出实际文件路径和关键函数。文件路径必须来自仓库真实内容，不能凭名称猜测。

### 9. 最后用几条主线收束

用简短的身份主线、文件主线、任务主线、状态主线或反馈闭环，帮助读者把前面的信息串起来。必要时提供一张术语对照表。

## 语言风格

- 使用简体中文，代码符号、文件名、函数名、接口名保持原文；
- 先讲结论和作用，再讲实现机制；
- 句子短一些，使用“它负责……”“这一步的作用是……”等直接表达；
- 少堆砌术语，必须使用的术语在首次出现时立即解释；
- 适当使用生活化比喻，例如“工厂”“档案盒”“装箱单”“工位任务”，但说明比喻对应的真实对象；
- 用自然段讲清楚因果关系，列表只用于并列信息，表格只用于真正的对照；
- 用流程图表达复杂关系，用具体例子解释抽象概念；
- 保持专业、平静、诚实，不使用宣传口吻，不把推测写成事实；
- 不把说明写成文件清单、调用栈堆积或代码逐行翻译。

## 结果质量检查

完成说明前检查：

- 读者是否能在开头说出项目解决什么问题；
- 每个核心模块是否说明了职责和边界；
- 关键术语是否在第一次出现时解释；
- 是否至少跟踪了一条真实或明确标注为示例的完整链路；
- 是否说明了输入、输出、状态、失败和重试；
- 图中的组件和箭头是否有代码或配置依据；
- 文件路径、函数名和 API 是否已经确认；
- 未确认的内容是否明确标成推断或待确认；
- 最后是否给出下一步代码阅读路线。

如果用户要求保存为 Markdown：使用用户指定的路径，不覆盖已有文件；文件开头写明保存日期和时间，并在回复中报告文件路径。除非用户要求，不要因为解释任务自动修改项目代码、运行破坏性命令、提交或推送代码。
